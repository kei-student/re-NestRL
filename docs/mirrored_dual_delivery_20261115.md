# 左右鏡映・両側配膳環境

ユーザーの指定に従い、左右の食材・調理台・配膳口の幾何配置を揃えた新条件を作成した。
layout IDは`mirrored_dual_delivery_v1`。既存Figure1条件、設定ファイル、成果物は保持する。
この変更は再現条件への追加実験であり、元論文のレイアウトとは区別する。

## 配置

7×8の厨房、中央x=3の通行不能カウンター、共有皿1枚は維持する。
左右の厨房間をエージェントが移動することはできない。
各部屋の12床からエピソードごとに独立・一様に開始位置を選ぶ。

| 対応する設備・食材 | 左（agent0/L1） | 右（agent1/L0） |
|---|---|---|
| トマト／にんじん | (0,1) | (6,1) |
| じゃがいも／ブロッコリー | (0,2) | (6,2) |
| レタス／玉ねぎ | (0,3) | (6,3) |
| 調理台 | (0,4) | (6,4) |
| 配膳口 | (0,5) | (6,5) |
| 固定開始を明示した場合 | (2,5)、左向き | (4,5)、右向き |

共有皿の初期位置は(3,3)。右側の開始方向を右向きにして、左右の初期姿勢も鏡映にする。
初期位置の乱数分布は両側で同じだが、2体の位置を常に鏡映で固定することはしない。

左・右のいずれかが、許可レシピの完成皿を自分側の配膳口へ置けば成功する。
`info.delivery_agent`と`complete`イベントの`agent`で配膳者0/1を記録する。
外部から完成皿を配膳口へ直接配置した場合など、実際の配膳actionが無い場合はnull。
正しくない組み合わせ、食材不足、余分な食材は両口とも成功としない。

## L0と同時操作

`ScriptedPeer`は自分側の食材を調理・共有皿へ投入し、指定の2食材が正確に揃うまで待つ。
完成皿を取得できたら自分側の配膳口へ運ぶ。左右のどちらを担当しても同じ手順を使う。
右L0・左L1という学習役割は今回の設定でも維持し、L1も左口から配膳可能になる。
契約は`configs/l0/mirrored-dual-delivery-recipe-pool-v1.json`。

PACEは同時操作をリスト順に実行するため、両者が空手で共有皿を同時取得すると
常にagent0が先に取得する。この新条件では、その競合時だけ実行順をepisode RNGで
等確率に選び、`shared_plate_contention.first_agent`を記録する。
両者による食材投入など、両者が空手でない同時操作は従来の順序を保つ。
同じseed/action履歴から競合結果と状態を正確に再現できる。
PACEの固定ソース自体は変更せず、元レイアウトの動作順も維持する。

## 観測と設定

配膳口を1個追加すると位置tripleが3要素増えるため、新条件の観測は**108次元**。
隠れた右口を含め、partial条件では従来と同じ可視領域でマスクする。
各レイアウトに対応するschema・次元の整合を設定読込時に検証する。

| [0,39) | 自分・相手、左右調理台、左右配膳口、皿、6食材の位置triple |
| [39,49) | 自分・相手の向きと可視フラグ |
| [49,61) | 6食材の調理状態・可視フラグ |

新schemaは`pace_dense_<partial/full>_96_plus_<reserved12/ingredient_locks12>_mirrored_dual_delivery_v1`。
MLP/GRU構成、action6、レシピ3種類、報酬係数、40step、5episode roundは維持する。
モデル入力とL2準備時のバッチ入力は設定の観測次元を使用する。

次の3設定を準備した。いずれもランダム開始・400更新/28,800,000steps、
construction seed101–104、validation111、test121–125を保持する。

- `configs/l1-mirrored-dual-delivery-full-400u-s101-20261115.json`

各設定のprofileは固有名である。将来の学習は同名の新output root/registryを使い、
`l1-construction-101`等の内部IDが同じでも既存run directoryへ書き込まない。
今回は環境の実装と検証であり、Cloud学習や400更新の研究runは開始していない。

## 比較の範囲と互換性

この変更で左右の設備・対応食材の位置と配膳可能性は揃う。
各側の3食材から調理台までの距離差は残る。食材名・レシピのPACEグラフと報酬計算も
保持するため、食材・左右交換に対する報酬時系列の完全同一性や、レタス偏りの解消は主張しない。
偏りへの効果は、この条件で新規学習したモデルを評価して確かめる必要がある。

旧条件は105次元、新条件は108次元で、config/schema/source hashも異なる。
**既存モデルの新環境への移植・途中学習の継続は不可**。新規初期化から学習する。
旧JSONのcanonical hashは、デフォルトのlayout/dimensionを省略することで維持する。
環境ソース変更により、旧条件の推論・復旧も旧runに記録されたソースを使う。
strict guardsは維持し、古いモデルの読込を迂回しない。

設定のcanonical SHA-256（新run/checkpointの契約）：

## 検証

3観測/制限条件×3レシピ×144 joint starts×配膳者2側＝**2,592ケース**で、
指定側から40step以内の配膳を確認する。鏡映した開始位置・配膳者間で完了stepが一致する。
両者を自律L0にしたケースでは両側の配膳を確認する。
同時皿取得のseed再現、128seedでの両勝者出現、partial/fullの両配膳口の観測、
不正皿の拒否、108入力の短い一時学習・strict CPU load・評価・bit-exact resume、
旧設定hash保持も確認する。これら一時学習は実験性能を評価する研究学習ではない。

実行結果：119 unittest中117成功・Docker opt-in skip2。
上記2,592ケース、108入力の学習/評価/CPU再開、既存レイアウトの回帰テストは通過。
`scripts/bootstrap_upstream.py`で固定PACE6ソースを照合し、
`scripts/check_workspace.py --device auto --allow-dirty`と`git diff --check`も通過した。
作業ブランチは`codex/mirrored-dual-delivery-20261115`。
